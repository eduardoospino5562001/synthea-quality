# synthea-quality

Data quality and integrity checks for CSV datasets generated by
[Synthea](https://github.com/synthetichealth/synthea).

Synthea produces synthetic patient records (not real people). This tool reads the
CSV export and reports **structural** problems: schema mismatches, broken
primary/foreign keys, missing required values, duplicates and impossible dates.

> **Status: Phase 1, under active development.** See "Development status" below.

## Scope

Phase 1 produces deterministic, reproducible findings that a human can review:

- dataset discovery (which tables are present, which are unknown);
- schema validation against an explicit, versioned schema contract;
- primary key checks (nulls, uniqueness) where a key is confirmed;
- referential integrity checks (foreign keys that point nowhere);
- deterministic data quality checks (missing required values, exact duplicate
  rows, fully empty columns, unparsable dates);
- temporal checks that have confirmed meaning (`START <= STOP`,
  `BIRTHDATE <= DEATHDATE`, events before birth);
- structured results, exported as Markdown (human) and JSON (machine).

## Explicitly out of scope for now

Following the guidance of the Synthea maintainers, Phase 1 does **not** implement:

- prevalence or incidence metrics;
- disease-rate validation, expected ranges or confidence intervals;
- statistical CI gates (Synthea is a stochastic simulator; a deviation is not by
  itself an error);
- dashboards, web UI, orchestration frameworks, distributed processing;
- FHIR/CCDA validation;
- any change to the Synthea generator.

These are candidates for later phases, not accidentally missing features.

## Requirements

- Python 3.11 or newer
- The only runtime dependency is `pandas`

## Install (development)

```bash
git clone <url> && cd synthea-quality
uv venv --python 3.11        # the declared minimum; keep the venv on 3.11
uv pip install -e ".[dev]"
.venv/bin/pytest
```

## Official sample data

Validation uses the sample datasets published by the Synthea project, not
datasets copied from other repositories:

- https://github.com/synthetichealth/synthea-sample-data/tree/main/downloads/latest

The `latest` CSV sample is generated automatically from Synthea `master` by the
project's own release workflow. Downloaded data is kept in a local working
directory (git-ignored) and is never modified.

## Reports

One run of the tool produces the same structured result in two forms:

| Output | Purpose |
| --- | --- |
| Markdown | for a person: scope and contract verdict, summary, findings, detail, what was deliberately not checked |
| JSON | for people and automation: versioned, deterministic, every metric and sample |

The pipeline is kept in separate layers: `data -> checks -> structured model
(DatasetReport) -> renderer`. The check modules only ever see data that was already
loaded, and the renderers only ever see a report: rendering reads no CSV, runs no
check and imports no data library, so the JSON of a report reproduces its Markdown
exactly. Every check identifier, metric and sample survives into the JSON; the
Markdown summarises passing checks by identifier and shows metrics and samples for
the findings.

A report states what was observed and never more: the contract result is
`COMPATIBLE`, `INCOMPATIBLE` or `UNKNOWN`, and `COMPATIBLE` is presented as evidence
of consistency among the tables the dataset actually contains, not as proof of the
Synthea version that produced it. Relationships the documentation describes but the
tool does not enforce are listed in their own section, marked as pending a
maintainer's confirmation rather than as dataset defects.

## Scalability

Loading reads a whole table into memory; chunking is deliberately not implemented
yet. It is not needed for the current MVP, which targets sample-sized datasets, but
the limit is measured rather than theoretical:

| Measurement | Result |
| --- | --- |
| One full `observations.csv` (1.78 GB, 10,209,651 rows x 9 columns) | 24.7 s, ~1.64 GB peak RSS |
| Key checks over the official sample (18 tables, 201,657 rows) | 1.1 s, ~103 MB peak RSS |
| Quality checks over the official sample (86 checks, 18 tables) | 3.0 s, ~144 MB peak RSS |
| Temporal checks over the official sample (19 checks) | 0.6 s, ~95 MB peak RSS |
| Key checks over a 2021 dataset (17 tables, 12M+ rows) | 65.0 s, ~772 MB peak RSS |

The key checks keep only compact parent key sets in memory and release each child
table before reading the next one. The quality checks need every column, so they do
load whole tables, but only one at a time: a dataset is never held in memory at once.
A dataset whose large tables are much bigger than the sample will need
chunked/streamed processing.
